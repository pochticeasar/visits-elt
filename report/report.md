# Лабораторная работа 2. ELT-пайплайн для пакетной аналитики над visits_v1

## 1. Задача

Данные Яндекс.Метрики `visits_v1` (TSV, 2.53 ГБ, 1 686 859 строк, 181 колонка)
загружаются в S3-хранилище в сжатом виде, затем Spark переводит их в вид,
удобный для аналитики. Аналитика выполняется в Jupyter.

Стек: Garage (S3), Spark 3.5.7, JupyterLab, Airflow. Всё запускается в Docker.

## 2. Пайплайн и слои

```
visits_v1.tsv ──load.py──▶ s3://raw ──transform.py──▶ s3://warehouse ──▶ Jupyter
 (диск, текст)              Parquet+zstd,                Parquet+zstd, типы,
                            как в TSV                    схлопнуто, по дням
```

| Шаг | Скрипт | Что делает |
|---|---|---|
| Extract | — | файл `visits_v1.tsv` на диске |
| Load | `jobs/load.py` | читает TSV потоком, режет на части по 131 072 строки, пишет каждую в Parquet+zstd в `s3://raw`, в конце пишет `manifest.json` |
| Transform | `jobs/transform.py` | читает `raw`, проставляет типы, схлопывает версии визитов, пишет `s3://warehouse` с партициями по дню |
| Analytics | `notebooks/analytics.ipynb` | запросы, графики, сравнение с несжатым TSV |
| Оркестрация | `dags/visits_elt.py` | Airflow DAG: `load → transform`, retries, оба шага идемпотентны |

### 2.1 Load: TSV → raw

* Значения **не меняются**. Все 181 колонка хранятся как `binary`, то есть как байты из TSV.
  В датасете много невалидного UTF-8, поэтому строковый тип здесь не подходит.
* Снимается только TSV-экранирование ClickHouse (`\t`, `\n`, `\\`, `\0`).
* Добавляются служебные колонки `_part` (имя файла) и `_row` (номер строки в нём).
  По ним виден исходный порядок строк, он нужен для схлопывания.
* Пути детерминированные: `raw/visits/batch=2014-03/part-00000.parquet` … `part-00012.parquet`.
  `manifest.json` пишется последним. В нём для каждой части: строки, байты, sha256, min/max даты.

Сжатие: 2534 МБ → 453 МБ (17.9%) за 28 с.

### 2.2 Transform: raw → warehouse

Сначала данные изучались. Что нашлось и что из этого следует:

| Факт | Следствие |
|---|---|
| 7 дней: 2014-03-17 … 2014-03-23 | партиция = день, ~64 МБ на день |
| 5 139 строк с `Sign = -1` | данные из CollapsingMergeTree, их надо схлопнуть |
| колонки `VisitVersion` нет, у сотен визитов `VisitID = 0` | ключ визита: `(CounterID, StartDate, UserID, VisitID)`, как `ORDER BY` в ClickHouse |
| по этому ключу `sum(Sign)` всегда 0 или 1 | правило схлопывания однозначно |

Что делает `transform.py` и зачем:

1. **Типы** по схеме ClickHouse (`jobs/schema.py`). Числа становятся `int`/`bigint`, даты — `date`/`timestamp`.
   Нулевые даты `0000-00-00` и пустые строки становятся `NULL`.
   `UInt64` (ID и хэши) становится `bigint` с сохранением всех 64 бит.
   *Зачем:* числа и даты в Parquet хранятся компактно, у них есть min/max-статистика, их не нужно парсить в каждом запросе.
2. **Массивы.** Текст `[1,2,3]` становится `array<int>`. Вложенные группы (`Goals.ID`, `Goals.Price`, … лежат в TSV
   параллельными массивами) собираются в один `array<struct>`.
   *Зачем:* цель визита — одна запись, а не 6 массивов, которые надо сопоставлять по индексу.
3. **Схлопывание.** По ключу остаются группы с `sum(Sign) > 0`. Из группы берётся последняя по `(_part, _row)`
   строка с `Sign = +1`, как `FINAL` в ClickHouse. 1 686 859 → 1 676 581 строк.
   *Зачем:* иначе каждый запрос должен помнить про `Sign`, и счётчики визитов будут завышены.
4. **Раскладка.** Партиции по `start_date`, внутри сортировка `(counter_id, start_time)`, zstd.
   *Зачем:* фильтр по дню читает одну папку; фильтр по счётчику отсекает лишние row group по min/max.

Время transform: 43 с. `warehouse`: 7 файлов, 448 МБ (17.7% от TSV).

Нюанс данных. Датасет анонимизирован, и строка-отмена иногда не совпадает с той,
которую отменяет. Поэтому `sum(Duration*Sign)` (608 551 464) и сумма длительности
последних строк (603 432 938) расходятся на 0.8%. Число визитов при этом совпадает точно.

### 2.3 Один визит через все слои

Пример из ноутбука, визит `counter_id = 10040391`, `visit_id = 7677919079884699762`:

| Слой | Как выглядит |
|---|---|
| TSV | 3 строки: 285867 (`Sign = -1`, 17 с), 285868 (`+1`, 1507 с), 1075542 (`+1`, 17 с) |

## 4. Сжатый и несжатый вид

Все 7 запросов аналитики выполнены в двух вариантах:

* **TSV** — исходный файл без сжатия в `s3://raw/tsv/`. Без transform каждый запрос сам
  разбирает текст, проставляет типы и схлопывает `Sign` (те же функции, что в `transform.py`);
* **warehouse** — результат transform.

Медиана 3 прогонов. «Прочитано» — `inputBytes` из Spark UI.

| Запрос | TSV, с | warehouse, с | Ускорение | TSV прочитано, МБ | warehouse прочитано, МБ | Ответ совпал |
|---|---|---|---|---|---|---|
| по дням | 2.91 | 0.27 | ×11 | 2 536 | 7.7 | да |
| источники | 3.87 | 0.22 | ×18 | 2 536 | 3.3 | да |
| устройства | 4.23 | 0.22 | ×19 | 2 536 | 3.7 | да |
| топ целей | 7.00 | 0.31 | ×23 | 2 536 | 17.1 | да |
| конверсия | 9.95 | 0.45 | ×22 | 5 071 | 26.3 | да |
| регионы | 5.06 | 0.20 | ×25 | 2 536 | 7.4 | да |
| день недели × час | 4.41 | 0.17 | ×26 | 2 536 | 8.4 | да |

Размеры:

| Слой | Строк | Файлов | Размер | От TSV |
|---|---|---|---|---|
| TSV | 1 686 859 | 1 | 2534.3 МБ | 100% |
| raw | 1 686 859 | 13 | 452.6 МБ | 17.9% |
| warehouse | 1 676 581 | 7 | 447.7 МБ | 17.7% |

Выводы:

* **Ответы совпадают во всех 7 запросах**: transform не потерял и не исказил данные.
* **Запросы быстрее в 11–26 раз.** TSV каждый раз читается целиком (2.5 ГБ),
  а из Parquet берутся только нужные колонки: 3–26 МБ, в 100–750 раз меньше.
* **Хранение меньше в 5.7 раза** (zstd).
* Разница в скорости будет расти с объёмом. На TSV каждый запрос повторяет весь transform,
  на `warehouse` эта работа сделана один раз.

## 5. Ограничения

* Один батч (одна неделя данных). Порядок версий визита задан порядком строк в файле:
  при нескольких батчах id батча должен сортироваться по времени.
* Невалидный UTF-8 сохранён в строковых колонках как есть.
* Справочник `TraficSourceID` восстановлен не полностью (коды 0 и 14).
* Spark в local mode: стенд на одной машине.

## 6. Как запустить

```bash
docker compose up -d --build
./garage/init.sh
# Airflow: http://localhost:8090 (admin/admin) → DAG visits_elt → Trigger
# или вручную:
docker compose exec jupyter python3 /opt/jobs/load.py --src /data/visits_v1.tsv --batch 2014-03
docker compose exec jupyter spark-submit /opt/jobs/transform.py --batch 2014-03
# JupyterLab: http://localhost:8888 → notebooks/analytics.ipynb
# Подробно: README.md
```
